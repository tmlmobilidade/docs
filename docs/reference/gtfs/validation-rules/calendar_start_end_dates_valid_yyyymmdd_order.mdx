## Propriedades da regra

| Propriedade | Valor |
|---|---|
| Rule ID | `calendar_start_end_dates_valid_yyyymmdd_order` |
| Ficheiro | `calendar.txt` |
| Campos | `start_date`, `end_date` |
| Tipo | Data |
| Severidade | Obrigatório |

**Descrição dos campos:**

- `start_date`: primeiro dia de serviço do intervalo.
- `end_date`: último dia de serviço do intervalo. Este dia está incluído no intervalo.

Mais informação em [calendar.txt](/reference/gtfs/schedule/calendar).

## Como funciona

O resultado depende da severidade definida na configuração da regra: obrigatório (`error`) reprova; recomendado (`warning`) passa com aviso; informativo (`info`) passa com informação. O aviso antecipa uma futura exigência, mas só reprova quando a configuração passar a obrigatório. Nos casos sem severidade explícita abaixo, a indicação de reprovação pressupõe a configuração obrigatória.

Quando chamada, a verificação avalia o preenchimento e o formato de cada data selecionada. Não compara a ordem entre a data inicial e a data final.

A regra avalia cada linha do `calendar.txt`, seguindo os passos abaixo por ordem, até um deles dar o resultado.

| # | Pergunta | Se sim | Se não |
|---|---|---|---|
| 1 | O campo selecionado está vazio? | Segue para o passo 2 | Segue para o passo 3 |
| 2 | A configuração da regra ignora a verificação ou proíbe o campo? | ✅ Passa sem reportar a ausência | Reporta o problema de data obrigatória ou recomendada em falta e termina |
| 3 | A configuração da regra proíbe o preenchimento? | ❌ Reprova e termina | Segue para o passo 4 |
| 4 | O valor representa uma data existente no formato `AAAAMMDD`? | ✅ Passa | ❌ Reprova: data inválida |

Esta verificação pertence a uma versão anterior e não é executada pelo fluxo atual de validação. Os passos abaixo descrevem o comportamento ainda existente quando a verificação é chamada. Os espaços não são removidos. A configuração informativa usa a mensagem de campo recomendado.

## Como se relacionam

Os campos delimitam o intervalo de serviço, mas são verificados em chamadas separadas. Apesar do nome desta regra, não existe comparação entre as datas.

## Exemplos

| `start_date` | `end_date` | Resultado | Porquê |
|---|---|---|---|
| `20261016` | `20261017` | ✅ Passa | Duas datas válidas |
| Vazio (data exigida) | `20261017` | ❌ Reprova | Data inicial em falta |
| `20260229` | `20261017` | ❌ Reprova | Data inicial inexistente |
| `20261016` | `20261017` (preenchimento proibido) | ❌ Reprova | Data final proibida |

## Como corrigir

| Problema | Causa provável | O que fazer |
|---|---|---|
| Campo obrigatório em falta | A configuração da regra exige a data | Preencher `start_date` ou `end_date` em `calendar.txt`. |
| Campo recomendado em falta | A configuração da regra recomenda a data | Preencher `start_date` ou `end_date` em `calendar.txt`. |
| Campo preenchido quando proibido | A configuração da regra proíbe o preenchimento | Remover o valor de `start_date` ou `end_date` em `calendar.txt`. |
| Data inválida | O texto tem formato incorreto ou indica uma data inexistente | Corrigir `start_date` ou `end_date` em `calendar.txt` para uma data existente no formato `AAAAMMDD`. |
