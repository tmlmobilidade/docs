## Regras de validação do campo pattern_id


### Campos que serão utilizados nesta regra

| Nome do Campo | Tipo | Presença    | Descrição                                                                                                                              |
| ------------- | ---- | ----------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `pattern_id`  | ID   | Obrigatório | Indica a variante de serviço em que a viagem opera na linha. <br/><br/>Não faz parte do GTFS standart, mas é obrigatório para nós TML. |



### O que esta validação faz 

O campo identifica a vista de padrão a que a viagem pertence: o desdobramento de uma rota por sentidos, quando aplica, de modo que viagens com o mesmo `pattern_id` representem a mesma sequência de serviço. No GTFS o campo é opcional; no vosso contexto pode ser tratado como exigido em feeds específicos. Nesta função só se verifica se o identificador vem fornecido; a coerência do padrão com `route_id`, `trip_headsign`, `direction_id`, `shape_id` e sequência de paragens não é feita aqui (outras validações podem cuidar disso).

---

#### Passa

- O `pattern_id` vem preenchido no ficheiro (há identificador de padrão na linha).
- O campo fica vazio e a regra dispensa a verificação (por exemplo, severidade de ignorar), pelo que a função não emite a mensagem de ausência e devolve o estado que o chamador use para deixar de seguir (no código, `false` quando falha a presença ou ignora, `true` quando o valor existe).

---

#### Falha

- Identificador em falta — o campo fica vazio, quando, para a severidade e regras, o preenchimento é obrigatório ou recomendado (o GTFS permite omitir, mas a regra de dados do projecto exige o `pattern_id`).
