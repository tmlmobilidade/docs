## Regras de validação do campo pattern_id


### Campos que serão utilizados nesta regra

| Nome do Campo | Tipo | Presença    | Descrição                                                                                                                                                 |
| ------------- | ---- | ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `pattern_id`  | ID   | Obrigatório | O `pattern_id` identifica a variante de serviço em que a viagem opera na linha. <br/><br/>Não faz parte do GTFS standart, mas é obrigatório para nós TML. |


### O que esta validação faz

Regra por linha em `trips.txt`: quando `shape_id` e `pattern_id` vêm ambos preenchidos, o valor de `shape_id` tem de ser igual ao de `pattern_id` (comparação de strings, carácter a carácter). Chave de regra: `shape_id_needs_to_be_the_same_as_pattern_id`; mensagem: `shape_id_same_pattern_id.not_matching`.

### Passa

- Se a regra estiver desativada / ignorada pelo `ShouldSkip()`. Porquê: não se aplica a validação neste feed ou neste contexto.
- Se `shape_id` ou `pattern_id` for nulo (qualquer um em falta). Porquê: a regra só impõe igualdade quando os dois existem; não força preenchimento do outro campo aqui.
- Se os dois existem e `*shape_id == *pattern_id`. Porquê: cumpre a convenção TML de alinhar o identificador da geometria com o do padrão.

### Falha

- Se os dois campos estão preenchidos e os textos diferem. Porquê: no perfil do projeto, o mesmo identificador deve servir de chave coerente para o padrão e para a shape; valores diferentes indicam inconsistência entre `trips.shape_id` e `trips.pattern_id`.

Nota: Isto não verifica se o `shape_id` existe em `shapes.txt` — só a igualdade literal entre os dois campos da mesma linha de viagem.
